Dedicated Server Save Sync coordinates the same Palworld world across multiple PCs without keeping a game server online 24/7 and without passing ZIP files around manually.

Download client Installation Architecture

Stop asking “which save was the good one?”

The backend keeps a single authority and every host must prove it started from the right version.

1 · status + lock
→
2 · download if needed
→
3 · PalServer + heartbeat
4 · save + shutdown
→
5 · ZIP + SHA-256
→
6 · upload with baseVersion

Designed to fail without silently overwriting progress

The hard part is not uploading a folder. It is preserving invariants across two hosts, unstable networks and failing processes.

Concurrency

Exclusive lock, TTL, heartbeat and optimistic concurrency through baseVersion.

Identity

Palworld uses worldGuid to prevent publishing the wrong world.

Atomic publication

Temporary ZIP, defensive validation, SHA-256 and SQLite-backed authority changes.

Recovery

History, restore as a new version, pending ZIP recovery and operational rollback.

External backup

Post-publication hook, timeout, audit trail and observable state. Works with tools such as restic.

Secrets

Bearer hashes server-side and DPAPI on Windows. Runtime files are excluded from source and release assets.

Self-hosted backend + Windows client

The backend stays available on the web. PalServer only runs on the PC hosting the current session.

Backend

git clone https://github.com/Ayerdi/dedicated-server-save-sync.git
cd dedicated-server-save-sync
cp .env.example .env
chmod 600 .env
config/deploy.sh --init-env
config/deploy.sh

Production: Docker Compose, HTTPS, private storage and Traefik/ForwardAuth or API-only mode.

Client

1. Download the v2.2.0 ZIP.

2. Copy config.example.json.

3. Configure the URL and PalServer.

4. Run Configurar-secretos.cmd and Probar-conexion.cmd.

5. Start with Iniciar-PalworldSync.cmd.

Palworld's local REST API must not be exposed to the Internet. Save Sync talks to it through localhost.

Backup status without fake certainty

The panel separates whether automatic backup is enabled now from whether the current version's hook reported success.

completed

A successful audited result exists for the current version.

pending

An active backup marker exists inside its valid time window.

unknown

Evidence is insufficient, for example after a stale marker. It is never presented as success.
