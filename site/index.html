Tu save autoritativo.

Dedicated Server Save Sync coordina la misma partida de Palworld entre varios PCs sin mantener un servidor de juego encendido 24/7 y sin pasar ZIPs manualmente.

Descargar cliente Instalación Arquitectura

Evita la pregunta peligrosa: “¿cuál era el save bueno?”

El backend mantiene una única autoridad y cada host debe demostrar que parte de la versión correcta.

1 · status + lock
→
2 · descarga si procede
→
3 · PalServer + heartbeat
4 · save + shutdown
→
5 · ZIP + SHA-256
→
6 · upload con baseVersion

Diseñado para fallar sin pisar progreso

El objetivo no es “subir una carpeta”, sino mantener invariantes incluso con dos hosts, red inestable o procesos que fallan.

Concurrencia

Lock exclusivo, TTL, heartbeat y control optimista con baseVersion.

Identidad

Palworld se valida con worldGuid para impedir que otro mundo se publique por error.

Publicación atómica

ZIP temporal, validación defensiva, SHA-256 y movimiento de autoridad dentro de transacciones SQLite.

Recuperación

Historial, restore como versión nueva, ZIP pendiente si una publicación no puede confirmarse y rollback operativo.

Backup externo

Hook post-publicación, timeout, auditoría y estado observable. Compatible con herramientas como restic.

Secretos

Bearer hashes en servidor y DPAPI en Windows. Los archivos runtime están excluidos del repositorio y de las releases.

Backend self-hosted + cliente Windows

El backend vive en una web siempre disponible; PalServer solo se ejecuta en el PC que aloja la sesión.

Backend

git clone https://github.com/Ayerdi/dedicated-server-save-sync.git
cd dedicated-server-save-sync
config/deploy.sh --init-env
config/deploy.sh

Producción: Docker Compose, HTTPS, almacenamiento privado y Traefik/ForwardAuth o modo API-only.

Cliente

1. Descarga el ZIP de v2.2.0.

2. Copia config.example.json.

3. Configura URL y PalServer.

4. Ejecuta Configurar-secretos.cmd y Probar-conexion.cmd.

5. Inicia con Iniciar-PalworldSync.cmd.

La REST local de Palworld no debe exponerse a Internet. Save Sync habla con ella desde localhost.

Estado de backup que no inventa certezas

El panel separa si el automático está habilitado ahora de si el hook de la versión actual confirmó éxito.

completed

Existe un resultado auditado correcto para la versión vigente.

pending

Hay un backup activo dentro de su ventana válida.

unknown

No hay evidencia suficiente, por ejemplo tras un marker vencido. No se presenta como éxito.

Proyecto terminado, no abandonado
